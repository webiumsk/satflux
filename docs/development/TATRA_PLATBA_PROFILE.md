# Tatra Platba description compatibility

## Observed format and accepted scope

The owner obtained a bank-direct private copy after the previous safe diagnostic
stopped at `transaction_description`. Only the public operation label and
anonymized structure are used here: `Popis transakcie: Platba N4/N6-N10`, followed
by a `QR-` reference containing 32 hexadecimal characters. Actual accounts,
references, amounts, dates and personal data are not copied into fixtures,
reports or repository artifacts.

The remainder has the already-supported greeting, credit header, three balances,
one `Ucet protistrany` field, bank signature, HTTP bank URL and optional
`Poznamka`/`Odporucame Vam` notices. This does not require new free-text parsing,
MIME decoding, raw retention or tail grammar.

Add only the exact case-sensitive operation label `Platba` to the existing
`CCINT|CSO` description alternatives. Keep the same four-digit bank code,
one-to-six-digit prefix and one-to-ten-digit account bounds. Require the same
complete frame, explicit reference provenance, positive credit/currency,
receiving account, cryptographic bank proof and contract-v2 provider checks.
No substring/reference fallback, arbitrary description, label alias or identity
migration is introduced.

## Identity and replay review

Existing CCINT/CSO parse outputs and credit fingerprints remain byte-identical.
Platba retains its literal label in the same existing v1 tuple; formatting and
reference changes within that type do not change the event key. Do not claim
that the three labels are equivalent or map Platba arbitrarily to one old type.

Independent review initially questioned the distinct label-bearing fingerprints.
Read-only provider evidence at e8d7fbc establishes that a label change alone with
the same authenticated reference cannot settle twice:

- References are generated by the provider or NOP, globally primary-keyed and
  bound to the original invoice and Store. The normal API cannot reassign them.
- The matcher locks the exact reference/Store and returns Duplicate for a
  confirmed request before inspecting the event key or invoking the recorder.
- Recording uses the reference as its stable payment ID and recognizes that ID
  during recovery after an external success and failed plugin commit.

A cross-invoice rendition would additionally need the bank to authenticate a
different valid invoice reference for the same economic credit, or unauthorized
reference reassignment. Neither capability is established by this incident.
That is a residual bank-reference-stability assumption, not a demonstrated new
vulnerability from the exact-label extension. Whole-frame rejection continues
to prevent reference injection through payer notes. Independent security accepts
this bounded design subject to frozen-source review and relevant replay tests.

The earlier alias-aware contract-v3/table idea is unnecessary for the demonstrated
issue and is not implemented. No provider source, database schema, package or
host pin changes. Existing current provider replay protections remain required.

## Ownership and validation

Backend owns the single parser alternative and bounded existing unit/native/MIME
tests. Main owns generated API digests, documentation, shared state and publication.
Independent QA/security review frozen source separately from implementation.

Require valid Platba QR/VS frames with the observed tail structure, exact old
output/identity goldens, same-type rendering/reference/numeric normalization,
near-match/malformed/injected descriptions and reference/tail rejection. Exercise
the normal native, fully signed MIME and fixed ASCII MIME paths with synthetic
data, preserving account/amount/reference/provider report binding. Verify same
reference with distinct label-derived keys, concurrent delivery and recorder
retry against the qualified provider where executable infrastructure is available.
Record actual executed results and limits separately; do not infer settlement
from a parser match or an HTTP intake acknowledgement.

All tests use isolated synthetic targets and existing locked dependencies. No
real transfer, bank-message replay, production access, forced confirmation or
historical payment mutation is authorized by these source changes. Actual
rollout and a later normal notification remain separate runtime verification.
