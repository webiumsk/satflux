## Disposition

**Conditionally acceptable architecture, with one blocking contract correction and explicit acceptance conditions below.** The reviewed text is not yet an implementation-ready one-shot contract because event-time NX does not survive early cache-key disappearance. This is design feedback, not implementation, deployment, activation or real-content-retention authorization. Explicit Product Owner approval of the new retention scope remains necessary after main incorporates the correction.

The default-off single-Store scope, rejection-only trigger, encrypted Redis storage, fixed CLI facts, no financial replay, no raw export and explicit backup caveat are appropriate. No existing security proof may change. `invalid_signature` does not establish forgery or bank origin; prior 18 synthetic assertions proved library PASS can still fail application policy. Capturing such input is diagnostic retention of untrusted private content, not payment evidence.

## D1 - Medium: an absent-key write can capture a second message

Evidence: proposal lines 27-36 promises the first message and one total record, using atomic create-if-absent; lines 54-57 require disabling afterward, but no durable automatic one-shot state is defined. Rollback deletion is mentioned at lines 78-80.

Scenario: the first capture succeeds; Redis evicts the key or it is removed before the configured future deadline. A second invalid-signature message reaches the handler while configuration remains enabled. `SET NX` sees absence and stores another private message. A crash between storing data and a separate disable operation creates the same gap. Relative TTL mistakes could additionally expire the first slot before the deadline and re-arm this path. Concurrency-safe creation alone does not enforce first-per-activation retention.

Impact: unexpected additional bank-content retention outside the promised first-message consent boundary; under normal processing each record could disappear while backups retain multiple encrypted snapshots. No demonstrated payment bypass.

Required correction: **activation creates an expiring ARMED slot; processing atomically changes only that existing ARMED state to CAPTURED.** Event processing must never create/recreate an absent slot. Bind immutable activation generation, selected Store and absolute deadline. Missing, expired, removed, evicted or malformed state fails closed. Concurrent losers cannot overwrite data. Use the same absolute expiration on transition, not a fresh duration. A retry/repeated activation with the same generation must not reset a captured slot or deadline; a deliberately new capture requires explicit fresh activation consent. This can be expressed without a schema migration. If a different implementation is selected, it must prove equivalent no-rearming behavior after cache loss and process crash.

Regression acceptance: concurrent first arrivals; duplicate/retried job; slot deletion/eviction after capture; missing armed slot; process crash at transition boundaries; same-generation activation retry; worker restart; exact deadline; all must yield at most one capture for that activation. Removing a diagnostic key while still enabled must not re-arm capture. Backup restoration after the deadline must remain unreadable/uncapturable to the command/handler.

## Mandatory acceptance conditions

1. **Absolute expiry is enforced as a decision as well as a TTL.** Persist an immutable activation time/deadline, validate deadline at most two hours after activation, and reject capture/read at or after it. Atomic state transition checks current trusted time against the same deadline and preserves its absolute expiration (for example Redis absolute expiration rather than resetting a two-hour TTL). An in-flight late job cannot store after expiry. Expired data restored from backup or temporarily readable due to lazy cache expiry still fails the explicit application check. Freeze timestamp units/precision and race behavior in tests; do not silently extend on config reload, access, write retry or clock/timezone conversion.
2. **Freeze the serialized/encrypted limit before implementation.** The existing 262144-byte MIME limit is not an encrypted-payload bound: JSON/base64/encryption add overhead. Define one numeric maximum for the complete final Redis value, including envelope and summary, and check it before write; reject oversized/malformed captures with a fixed status and no fallback. Avoid unbounded child output, duplicated raw text or serialized arbitrary library objects. Encryption and validation failure must preserve existing review/retry behavior. No raw payload goes to Redis command arguments, debug logging or plaintext cache fallback.
3. **Authenticated encryption covers the complete private envelope.** Original MIME, recipient, capture time and summary are encrypted together and bound to schema, selected local Store, activation generation and deadline. Validate these bindings on decrypt; another Store's ciphertext or an earlier activation cannot be analyzed through the selected slot. Store and route ownership come from server resolution, not message or subprocess fields. Preserve exact received MIME bytes; no trim/reconstruction or ordinary forwarding. Keep the application encryption key out of cache/logs/arguments, and use existing key management rather than creating ad hoc credentials.
4. **Small fixed diagnostic schema only.** At most the existing five DKIM signatures, each mapped to explicitly enumerated verdicts and primitive booleans/unknown states. Do not coerce arbitrary library values. Missing coverage fields are unknown/failure, not a successful comparison of two missing values. Library `status=pass` must be labelled separately from full application eligibility. `status.aligned` is a domain string/false in mailauth 8.0.4; emit only the derived fixed boolean/unknown, never the value. Exclude `b`, `bh`, selector/domain/address/header values, exception comments, DNS record, key, canonicalized headers and decoded body. Preserve a bounded original-check summary separately from a later recheck, with fixed provenance labels. A cryptographic verdict may be unknown/not evaluated rather than false. Validate malformed fields and oversized result arrays before either retention or CLI output.
5. **CLI verification cannot reach financial processing.** Accept only the selected activation/slot through server-side operator configuration; no arbitrary Redis key, path, URL, raw MIME argument, public endpoint or general export. Authenticate envelope/owner/deadline before analysis. Invoke only bounded verification/structural routines, not intake/import/report code or a queue dispatch. Recheck DNS must retain existing bank-name allowlist/budgets, with no new arbitrary callbacks or provider API. Read failure emits only a fixed code; exception/debug handlers must not print decrypted values. Shell access is the existing operator trust boundary; this feature does not create access control against an operator already holding application decryption keys.
6. **Operational privacy limit is explicit consent.** Two hours bounds the live slot and normal command access; it does not erase Redis RDB/AOF/replicas/backups, job ciphertext already in the existing queue, process memory or operator captures. Existing infrastructure retention, authorized backup access and application-key lifetime govern residual ciphertext recovery. Do not promise secure erasure or change backup/Redis policy silently. Verify the actual private Redis target, persistence/backup policy and key access before activation; disclose meaningful retention facts/unknowns to the owner. Rollback disables the activation first, then removes only its diagnostic slot if requested; no cache flush, queue deletion or financial record change.
7. **Trigger remains narrowly untrusted.** Require the server-resolved selected Store and exact invalid_signature outcome; no Company capture, caller mode or public flag. An unauthenticated-to-the-bank sender able to deliver to the route could consume the diagnostic slot first; even genuine Mailgun delivery cannot establish bank provenance. Expose at most a fixed consumed/unavailable state to the operator and promise no guaranteed bank message capture. Do not auto-rearm after irrelevant/hostile content or require a new real transfer.

## Proposed review and test gates after owner scope approval

Freeze file ownership, schema, final encrypted byte bound, activation state machine and read-only diagnostic call graph. Independent QA should exercise a disposable Redis with real atomic concurrency and expiry semantics, plus synthetic DB/Node targets. Required cases include disabled defaults; exactly selected Store isolation; malformed/forged activation/ciphertext; no-key/no-overwrite/no-rearm; Redis unavailable/timeout/eviction; deadline boundaries and restored expired record; oversized encrypted value; hostile MIME and malicious per-signature metadata; immutable original summary versus changed recheck; and absence of provider calls, transaction writes, queue dispatch or plaintext artifacts. Keep existing positive verification, review and retry regression coverage unchanged.

Security review must be independent of implementation and inspect final hashes plus complete command output/exception paths. Existing review-only MIME consumption must remain unchanged when capture is disabled or fails. Implementation requires independent QA/security and fresh exact-head CI; publication, deployment and activation remain main/owner gates.

No tests were run for this design-only review. Findings are supported by the proposal's stated state machine and cache semantics, not a claim that an unimplemented exploit was reproduced. No implementation approval is issued. Main can resolve D1 by documenting the ARMED-to-CAPTURED contract and incorporating the required bounded conditions before presenting the concrete proposal for new-scope approval.
