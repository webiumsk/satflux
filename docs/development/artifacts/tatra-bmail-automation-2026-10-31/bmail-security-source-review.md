## Disposition

Accepted for the bounded source security gate. No unresolved blocking security finding was verified in this snapshot. This is not a whole-application security approval or a claim that a current Tatra message has passed in production. The new automatic path is structurally defensible and useful for the supported profile; manual-only quarantine was not the completed product goal.

The earlier broad claim that choosing another invoice reference necessarily steals money is withdrawn. A debtor may legitimately choose the invoice reference. The payment must be a real authenticated bank credit to the correct receiving account, for the required amount/currency, allocated once. Previous synthetic attacks demonstrated reference-selection ambiguity, not fabricated funds, underpayment or cross-tenant theft. The design review in bmail-security-design.md records that correction and its evidence.

## Findings resolved during this review

**Medium  -  decrypted mail could survive through failed exception persistence.** The first MIME job catch rethrew arbitrary downstream exceptions; an exception message/previous chain containing decoded bank text could reach failed_jobs or an exception reporter despite an encrypted job field. Final app/Jobs/ProcessBankNotificationEmail.php:72-85 replaces that error with a fresh generic RuntimeException, without a previous exception, and logs its class only. The job retains ciphertext rather than mutating its public payload to decoded text. The synthetic private-marker regression in BankMimeConfirmationTest checks exception text, previous-null and serialized-job privacy. This closes the observed persistence path; memory inspection and unrelated provider logging are outside this gate.

**Low  -  forced QR lowercase could miss an uppercase provider reference.** The initial strict parser lowercased QR hex while provider NOP references can preserve uppercase and are matched by exact SQL equality. Final TatraBankSepaEvidenceParser.php:74-76 preserves the exact bank field; parser and actual native-webhook regressions cover uppercase. This was an availability/compatibility issue, not an unauthorized paid transition. The fix does not weaken tuple identity or the structural grammar.

## Verified boundaries and evidence

- BankInboundWebhookController.php authenticates the existing Mailgun timestamp/token HMAC before MIME dispatch and preserves existing replay checks. It never promotes arbitrary Authentication-Results/Pass headers to bank identity. The dedicated .mime route requires original body-mime and stores it encrypted before queueing. bootstrap/app.php exempts this field from trimming so DKIM bytes survive.
- runtime/bank-mail-verifier/verifier.mjs verifies the original UTF-8 MIME bytes using locked mailauth8.0.4 strict per-signature DKIM results. It requires a passing bank-domain aligned signature, SHA256 RSA/Ed25519, valid supplied time constraints, no body-length l= signature, equal canonical body coverage and signed unique From/To/Subject plus every present MIME interpretation control. Pinned library bytes were inspected: signingHeaders.keys is a colon-delimited string, canonBodyLengthLimited distinguishes l= and signatureTimeValid is true when optional time constraints are absent. This is not inferred from moving documentation.
- Only one explicit plaintext part is accepted; duplicate singleton headers, ambiguous recipients, HTML, multipart, attachments, disallowed charsets and malformed wire syntax fail closed. The signed To must equal the resolved route recipient; a valid bank message cannot be retargeted to another store merely by replacing the Mailgun recipient field. The PHP service checks the verifier digest against the exact original MIME and independently checks bank sender/domain before setting its private verified marker.
- MIME/signature/DNS budgets limit input, parsed output and network work. DNS is restricted to bank DKIM TXT selector names, with bounded lookups/deadlines; temporary DNS failure is retryable and never paid. Invalid results cause a generic review event without raw content. Production CLI cannot receive resolver/test configuration through its JSON/argv contract; the public-DNS fixture preload is test-only. Deployment process environment remains a trusted boundary.
- BankMimeVerificationService.php:74-105 uses argv/stdin through Symfony Process, a 15-second deadline, and a combined 300000-byte stdout/stderr cap. The streaming callback clears Symfony buffers, retains only bounded stdout and terminates on excess; no raw exception/output enters application errors. CLI and PHP failures preserve generic queue retry semantics.
- TatraBankSepaEvidenceParser.php operates on original decoded text rather than generic normalized HTML. It requires the complete ordered greeting/positive EUR receiving-account header/three numeric balances/constrained CCINT or CSO numeric description/reference prefix. It rejects duplicate, reordered, missing, encoded or nested structural fields and reserved labels in free-text tails. Only that bounded field supplies SEPA reference evidence; permissive company import metadata/toRow remains separate.
- The receiving IBAN is observed and checksum-normalized, not copied from settings. The existing contract-v2 provider remains responsible for original invoice/store/account/amount/currency authorization. Missing origin, unsupported grammar, unknown settlement and unavailable dependencies never become a paid claim.
- The new conservative bank-credit fingerprint excludes invoice reference, free remittance, delivery ID, body rendering and row index. It canonicalizes numeric/date representation and includes receiving account, minute, credit, balances and constrained counterparty tuple. Thus an altered candidate/note cannot give the same represented credit a fresh identity. It is explicitly not a bank-issued transaction ID; indistinguishable tuples may collide and require review. Provider duplicate evidence for another invoice must leave that invoice unpaid; duplicate is not proof of its settlement.
- No new session/CSRF, plan, entitlement, recovery phrase, Cashu, merchant-key storage or administration path was introduced. Existing native-MTA authentication and generic company importing remain separately trusted legacy channels; this review does not newly certify their external operator configuration.

## Assumptions, limits and next gates

- The two independent historical integrator templates and current official Tatra description-code documentation support the bounded structure. No current original local bank EML exists. QR in that reference slot is a synthetic supported adaptation, not a witnessed current-bank notification. Strict signed To/Subject/MIME and plaintext requirements may reject current messages. This limits operational interoperability, not structural safety; privately verify a current real delivery before claiming active automatic coverage.
- The explicit Mailgun .mime route, locked nested runtime installation and controlled Node process environment must exist in deployment. No production settings, inbox, DNS bank lookup, real funds, signature or merchant message was tested.
- DKIM authenticates bank-origin signed content, not irrevocability of a credit or universal bank notification uniqueness. The tuple deduplication schema is conservative; current bank formats with changing balance representations require separate evidence/profile review. No proof of all repeated notifications for one bank transaction is claimed.
- Queue APP_KEY, encrypted data backups and existing provider database/Data Protection recovery remain operational requirements. This change adds no raw MIME archive or retention service. Generic company import payload/logging and the protected native-MTA adapter are pre-existing channels, outside this new MIME privacy approval.
- The snapshot excludes changing generated API/locale/documentation files from its 24-file source digest. Main owns those gates and must ensure reviewed source hashes remain unchanged at commit. Full installed-host/payment reconciliation, final DLL/archive byte qualification, CI and deployment remain separate.

No source implementation, Git, shared-state, production or external application writes were performed by this reviewer. Graphify was queried from the existing primary graph but returned unrelated nodes; the worktree has no graph. Targeted reads followed without graph installation or rebuild.
