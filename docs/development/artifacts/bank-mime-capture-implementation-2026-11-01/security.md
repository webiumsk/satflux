## Verified security properties and attack scenarios

1. **One owner, one capture and immutable deadline.** `BankMimeCaptureService.php:20-41` uses atomic operator NX arming and an exact-current-ciphertext XX transition. The transition validates actual absolute Redis expiry against the authenticated deadline and current Redis TIME. Missing/evicted state never creates a replacement. Lines 59-64 derive activation/deadline from Redis; lines 235-266 validate exact schema, Store/current-user owner, generation, timestamps, digest, summary, physical expiry and recipient ownership. Lines 205-209 suppress summaries if the record disappears or expires during recheck. Attack scenarios reviewed: concurrent deliveries, replay of an old token after a fresh activation, cache eviction, changed Store owner, modified ciphertext, restored expired envelope and longer external TTL. These fail closed; no TTL extension or automatic rearm. Regression coverage passed independently, including real Redis concurrent arming/capture and exact-expiry assertions.
2. **Whole-envelope encryption and numeric storage bounds.** Service lines 108-125 and 198-202 enforce 262144 raw bytes and 1048576 bytes for the final encrypted string, with original bytes base64 preserved inside authenticated encryption together with owner/generation/deadline, recipient, digest and original safe summary. State is one constant prefixed cache key, not a merchant identifier in a key. Oversize, decryption, schema, cache or encryption failures return fixed statuses and preserve the existing bank decision; no file/plaintext fallback exists. Attack scenarios reviewed: raw overflow, ciphertext overflow, metadata substitution and invalid recipient/owner binding. Independent tests validate limits, complete private-envelope encryption and retained ARMED state on capture failure.
3. **Safe diagnostics across both process and CLI boundaries.** `BankMimeDiagnosticRunner.php:38-64` binds the child envelope to PHP's exact raw SHA256 and requires the summary/outcome to agree. Lines 68-109 rebuild only exact known keys, five signatures maximum, six fixed header names, enum verdict/reason and boolean/null facts. Unknown strings become literal unknown; malformed types/extra fields fail validation. Lines 23-35 and 112-139 sanitize exceptions, use stdin instead of raw process arguments, bound execution/output and discard stderr. Node `verifier.mjs:187-230` projects only these facts, with missing body/hash fields remaining null. Attack scenarios reviewed: injected comments/headers/domain/selector/key/private output, arbitrary enum strings, wrong scalar/container types and child content binding mismatch. Independent PHP tests and 36 independent Node assertions passed; no secret, address, original MIME or raw verification payload enters operator output.
4. **Financial proof, retry and isolation preserved.** `BankMimeVerificationService.php:123-159` uses diagnosis only for an existing matching ARMED slot; transport/schema/cache failure falls back to strict verification. A validated invalid_signature result alone may be captured, and capture exceptions cannot alter the rejection. Lines 146-169 preserve exact status handling and the existing verified-field/hash/sender binding checks. Node evaluates the unchanged full proof predicate before its optional guarded observer; `verify()` still returns only its original contract. A crypto PASS missing required signed fields remains invalid_signature; future constraints, tampered bodies and temporary failures retain their existing outcome. The three operator commands expose no intake/import/provider-report/queue-dispatch/raw-export path. Independent feature tests include an actual signed Node message remaining verified and ARMED, followed by a tampered message remaining review-only and becoming CAPTURED, with zero financial import/provider/queue side effects.
5. **Existing boundaries outside capture unchanged.** Static byte comparison passed for strict CLI, company CLI/extractor, package and lock, ProcessBankNotificationEmail, inbound webhook controller, address/inbound services and SepaEmailConfirmationService: ten files unchanged from baseline. Authentication/CSRF/routes, queue encryption/sanitization, Store/Company split, existing support exception, merchant keys, recovery phrases, billing/entitlements and Evolu were not expanded by this diff. This bounded review does not claim a fresh whole-application audit of those unchanged systems. ## Assumptions, dependencies and operational blockers

Requires an existing private Redis 7-compatible connection supporting PEXPIRETIME/PXAT and the existing application encryption/key protection; older/failed Redis fails capture closed before ARM writes, while normal bank verification remains available. Actual production version, private connection, persistence/replication/backup retention and key-access policy were not accessed. The tested application connection uses phpredis; no additional dependency was installed. Operator shell access remains the existing trust boundary; no claim is made to protect plaintext from an operator already holding application keys.

All workers consuming the webhook queue must have the reviewed runtime/locked dependencies before a separately approved activation. Default remains off. The owner must explicitly acknowledge backup residuals when arming; live two-hour TTL and command expiry checks do not promise erasure of RDB/AOF/replicas/backups or process memory. Main's implementation document makes this clear. No extra real transfer, ordinary forwarding/reconstruction or financial replay is needed or authorized.

The actual latest bank EML/signature/layout and precise historical rejection remain unverified. An attacker-delivered message with no eligible bank proof can consume the selected diagnostic slot first; this is disclosed untrusted diagnostic input and cannot authorize payment. No guaranteed bank notification arrival/capture is claimed. After scope approval, only the separately approved operational window may retain one such message; this review does not activate it or recover any earlier consumed notification.

No unresolved source security blocker remains. Final independent QA, complete fresh exact-head CI and main's applicable publication/rollout/activation gates remain outstanding outside this reviewer assignment.
