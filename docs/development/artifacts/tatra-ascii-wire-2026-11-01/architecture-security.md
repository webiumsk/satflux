## H1 - High if implemented: unsigned controls select payment text

Evidence: current `runtime/bank-mail-verifier/verifier.mjs:119-141` admits MIME controls and obtains `parsed.text` through mailparser; lines 155-178 currently require present MIME controls in the same proof before returning that decoded text. This current enforcement prevents the proposed naive bypass; this report does not identify a vulnerability in the current source.

Attack: a transit actor changes an unsigned Content-Transfer-Encoding or charset while leaving signed body octets and signed From/To/Subject unchanged. DKIM can still pass while the decoder returns different text. If the MIME signature requirement alone is removed, the signed proof no longer binds the interpretation presented to the credit parser. Potential impact is misinterpreted amount/reference/content; exact financial exploitability depends on the existing strict parser and is not claimed from a toy example. Required mitigation is fixed header-independent interpretation, not a general MIME requirement removal.

Reproduction: independent synthetic RSA/TXT fixture changed unsigned CTE from 8bit to quoted-printable. Both real mailauth verifications passed with the same canonical body hash; real mailparser returned different text. The research probe prints only a fixed assertion summary and no decoded values. Regression must require unchanged output or rejection for every unsigned-header mutation; a passing signature must never allow an attacker-selected alternate decoded payment body.

## Standards and local dependency evidence

DKIM authenticates canonicalized wire octets without MIME decoding. Simple removes terminal empty lines; relaxed additionally reduces ASCII SP/HTAB and line-end whitespace. Missing `c=` defaults to simple/simple; one-component `c=relaxed` means relaxed headers with a **simple body**. Body-length limits permit unsigned tails. Signing MIME controls is advised. These are the relevant constraints, rather than a standard-defined payment profile. [RFC 6376 sections 3.4, 3.5, 3.7 and 5.4](https://www.rfc-editor.org/rfc/rfc6376.html).

MIME 7bit/8bit are identity transfer encodings; QP/base64 transform content. Their labels do not authenticate a charset or bank interpretation. The 7bit/8bit definitions bound lines and disallow NUL/bare newline forms. [RFC 2045 sections 2.7-2.8 and 6.2](https://www.rfc-editor.org/rfc/rfc2045). UTF-8 decoding must reject invalid sequences rather than accepting overlong/surrogate encodings. [RFC 3629 sections 3-4 and 10](https://www.rfc-editor.org/rfc/rfc3629.html).

Pinned installed mailauth 8.0.4 source inspected read-only in the existing dependency checkout:

- `dist/esm/dkim/dkim-verifier.js:244-251` normalizes the two canonicalization parts using `getBodyCanon`; lines 603-610 expose raw `format` (`c=`), `bodyHash`, `bodyHashExpecting`, status and signature-time validity. Lines 615-630 expose hashed/total canonical byte lengths and whether `l=` limits the body. `format` alone is not a canonicalized body or trustworthy decoded text.
- `dist/esm/dkim/body/simple.js` and `relaxed.js` implement body hashing. Their `digest()` functions do not return canonical body text. `BodyHashStream` forwards original chunks, so its output must not be mistaken for canonicalized bytes. Do not monkeypatch private hasher internals in production to obtain text.
- Body-hasher SHA256: simple `1a1484ec528d14769fb5de2c596ea25b69043ceae022f6b9b20705657c162429`; relaxed `c37e171401581cafe8a2efff3ac4db96f9925677d4c4ef7f23d1de87f82e7ffb`. Current verifier SHA256 `0a1ea5b71bd8903af8983253abd8203bfbf4f38ffd83c3dab70107c0f25c99da`.

## Minimum safe alternative contract

1. **Retain the current fully signed MIME path.** It continues to support its already tested plain UTF8/ASCII QP/base64/identity decoding only when one eligible signature covers every required identity/MIME field. Existing Company import is untouched. Do not make a failing strict MIME interpretation silently equivalent to a broadly decoded fallback.
2. **Add a distinct identity wire profile, not a generic MIME fallback.** Server policy defines its text semantics unconditionally. It may be admitted only for the narrowly observed single text/plain, declared UTF8/ASCII and 7bit/8bit identity format, with duplicate/ambiguous controls, binary, multipart, HTML/attachments or unsupported charset/encoding rejected. Unsigned metadata can only disqualify a message; no admitted header value selects a decoder, body part, charset, line transformation or alternative output. Changing an admitted header must leave the same fixed text or cause rejection. A sender/Mailgun-supplied mode flag cannot select it.
3. **One complete bank proof.** Keep bank signer allowlist, independent sender alignment, recipient equality, signed From/To/Subject, strict DKIM, allowed algorithm/minimum key, signature-time validity, DNS budgets and no `l=`/partial coverage. All proof conditions come from one signature. Never mix signed headers or body evidence from several results. Diagnostic booleans or supplied Authentication-Results are not proof.
4. **Canonical bytes tied to that same proof.** Extract the complete original wire body at the single validated CRLF/CRLF boundary. Determine the supported body mode from that proof's authenticated `c=` semantics: second component, default simple when absent; do not use the last component for a one-component value. A small bounded byte canonicalizer may be separately implemented and tested for only simple/relaxed. Require its SHA256 to equal both the selected successful proof's `bodyHash` and `bodyHashExpecting`, with strict base64/hash shape validation. Require exact integer equality of computed canonical length, `canonBodyLength` and `canonBodyLengthTotal`, and `canonBodyLengthLimited === false`. Missing/unknown fields, mode or mismatch reject. The hash cross-check is required even if a local canonicalizer appears RFC-correct.
5. **Decode canonical bytes as fixed fatal UTF8 identity only.** No quoted-printable/base64 decoding, MIME charset conversion, HTML/entity handling, Unicode normalization, BOM stripping or soft-line joining occurs in this branch. ASCII is simply a subset. Preserve a BOM for later rejection rather than allowing a default TextDecoder to strip it unexpectedly; a fatal UTF8 decoder with explicit BOM behavior or a byte roundtrip check is appropriate. Reject invalid UTF8, NUL/binary/control/confusable-format content under the existing strict text rules. For this narrow profile require original MIME at most 262144 bytes, both wire body and returned canonical body at most 65535 bytes, and at most 998 octets per CRLF-delimited body line. Relaxed handling concerns only ASCII SP/HTAB, not Unicode whitespace. Empty/nonmatching text cannot establish a credit.
6. **No representation ambiguity or signature-order selector.** Prefer the original strict path where a fully eligible signed-MIME proof exists. If several eligible identity proofs yield different canonical body bytes, reject as ambiguous instead of letting unsigned DKIM-header ordering choose a text. Do not opportunistically try identity, QP, base64, HTML or charsets until some parser matches. For an unsigned declared QP/base64/foreign charset, fail closed under this proposal; knowing that the wire bytes are ASCII is insufficient to infer identity encoding.
7. **Preserve transport binding and financial identity.** PHP's existing `contentSha256` remains the hash of the exact original MIME for subprocess binding, not the canonical-body hash. The latter is a separate internal proof check and must not be exposed in logs. Route owner binding, encrypted queue/capture, original-versus-recheck diagnostics, unknown/transient retry behavior, account/amount/reference validation and once-only provider reporting remain unchanged. Canonicalization must not introduce a new financial dedup schema or reallocate a previously consumed credit.
8. **Strict bank layout still required downstream.** `TatraBankSepaEvidenceParser.php` requires its bounded ordered classic bank-owned fields and forbids control/format/HTML/entity ambiguity; `TatraBankEmailParser.php` only attaches E2E/explicit VS/credit identity from that evidence. Compact parsing remains explicitly noneligible. `SepaEmailConfirmationService.php` still requires positive credit, explicit currency, original receiving account, unambiguous bank-owned reference and compatible provider contract. Authenticating wire text does not by itself qualify the observed current template or mark payment paid.

This contract is an application-specific inference from cryptographic coverage and the existing parser invariants, not a claim that RFCs endorse this banking use. It deliberately trades unsupported formats for fail-closed behavior. A separate implementation authorization/review must freeze the exact profile and tests before source changes.

**Final architecture disposition: ACK for the narrower ASCII/7bit/relaxed candidate. No remaining blocking design issue before the authorized source implementation.** This supersedes the earlier unknown-format blocker and broad identity-profile proposal for this change. It is not final code acceptance or deployment/financial authorization.

The accepted candidate preserves the complete existing signed-MIME legacy path and its precedence. Its new Tatra profile admits only the observed root plain UTF8/MIME1.0/CTE7bit format, validates the entire original body as printable ASCII plus SP/HTAB/CRLF with no bare CR/LF or other controls, and retains bounded raw/body/line lengths. It derives exactly one fixed relaxed canonical body independent of unsigned MIME interpretation. It may restrict the entire authenticated c= representation to relaxed/relaxed, as observed. The same otherwise eligible bank signature must supply signed From/To/Subject, bank signer/alignment, allowed algorithm/key/time, no l=, complete coverage, and the matching canonical SHA256/bodyHash/bodyHashExpecting and both exact canonical lengths. Returned body is this canonical ASCII text, never mailparser's decoded text. Transport contentSha256 stays the exact raw MIME digest.

Restricting every eligible new-profile proof to relaxed body canonicalization makes all such proofs derive identical text; signature ordering or removal cannot choose between simple and relaxed bodies. Thus the earlier mixed-body-mode ambiguity rejection is unnecessary for this narrower candidate, while cross-signature proof synthesis remains prohibited. Fully signed legacy behavior keeps its existing precedence and supported encodings. Nonobserved unsigned 8bit/QP/base64/charset/multipart profiles remain rejected, with no decoder guessing or parser/dedup/provider policy expansion.

Required final code tests retain all prior gates and specifically verify: unsigned7bit positive; every unsupported unsigned encoding and charset negative; header mutation either rejection or identical canonical ASCII output; relaxed WSP equivalence; same-proof canonical digest/length mismatch; mixed signatures and no coverage synthesis; default/one-component/simple c= not entering the new branch; all original crypto/time/recipient/key/l=/retry negatives; signed-MIME branch result stability; and cross-profile financial identity/replay behavior. Independent security/QA must review frozen implementation hashes before publication/rollout.
