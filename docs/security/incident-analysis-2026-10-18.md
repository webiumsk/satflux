## Findings

### Confirmed repository defects and focused fixes

- **Guest store-limit race.** `EnsureStoreLimit` previously counted a guest's stores and then continued into remote BTCPay provisioning without serializing the count and create operation. Concurrent requests could both pass the one-store limit. A shared cache lock now spans the guest count and downstream request; lock acquisition timeout returns a retryable `503`. Guest Point of Sale creation already had a similar store-scoped lock added during this investigation. The lock depends on all application workers sharing an atomic lock-capable cache. Its lease is 30 minutes; provisioning that exceeds the lease remains a residual concurrency risk.
- **BTCPay Files fallback boundary.** `BtcPayFileUploadService::uploadForStore` previously relied on HTTP-route checks before invoking a server-key fallback. Current routes enforce authenticated, verified, non-guest ownership; the service now repeats actor, guest, and owner checks before any provider request. It rejects invalid uploads, unsupported MIME types, and files over 5 MiB. The provider call remains a fixed `POST /api/v1/files` with only that file; no caller-controlled destination/path is passed to the server key. The reviewed callers add a 10-per-minute route throttle. No cross-store read/overwrite path was found, and the log alone does not establish exploitation. The new service tests cover anonymous, guest, and foreign-owner rejection, owner fallback, invalid MIME, and oversized files.
- **Webhook identity.** Signature validation already used raw-body SHA-256 HMAC and `hash_equals` before event persistence or job dispatch. The controller now also rejects a valid globally signed request for an unknown store before side effects, with an exception only for the exact configured subscription store. A regression covers a subscription-secret signature paired with another store ID. Optional `deliveryId` remains accepted, so signed requests without it are not deduplicated; semantic event idempotency remains a follow-up risk.
- **BTCPay apps redirect.** `AppService::listApps` used `/stores/{id}/apps`, a web UI path, and only fell back to Greenfield on 404. It now calls `/api/v1/stores/{id}/apps` directly. `BtcPayClient` disables redirects. Historical `Location` was not captured, so its destination cannot be reconstructed from the supplied logs; the runbook provides a no-follow probe against the configured BTCPay origin.
- **Production log exposure.** Routine BTCPay client logs now keep only method, status, and a redacted endpoint template; the 422 body log was removed. App create/update logs no longer serialize merchant app configuration, names, response bodies, or raw BTCPay IDs. Store inventory logs now retain counts instead of complete BTCPay/local ID lists, and per-store inventory INFO entries were removed. Normal subscription 404 lookup no longer logs the email/customer selector or provider response. These are targeted reductions; this report does not claim every application log is free of identifiers.
- **Expected subscription 404.** `SubscriptionController::details` maps BTCPay subscriber `404` to an empty billing state (`subscriber: null`, zero credits) and does not downgrade local entitlements in that branch. This is normal for a registered user without a subscription. A test now verifies this response. The supplied logs do not connect the reported user ID 77 to those requests.
- **CashuMelt HTTP 400 retry loop.** In plugin code, a permanent quote-poll 400 was marked `FAILED/mint_poll_error`, but the checkout poller and a direct automatic retry path could continue polling; the reconciler runs its stale funding poll every third 45-second tick (about every 135 seconds). The plugin now puts this error into manual review, makes checkout polling return the saved error without calling the mint, skips it in reconciliation, and guards automatic retries even for upgrade-era rows that lack `NeedsManualReview`. Explicit merchant retry remains available and rechecks the same original quote. A 400 is not treated as proof that the invoice is unpaid; unresolved-funds safeguards remain.

### Suspicious but unconfirmed behavior

- **Guest accounts 68–76 and Lightning Address values.** Guest creation intentionally allows synthetic `guest+...@satflux.io` accounts without real email verification. A same-session retry reuses the guest; a new unauthenticated session can create a new guest. Existing guest-start/recovery limits are five requests per minute by request IP. This does not establish automation. The supplied October 18 Laravel and BTCPay log files contain no matching user IDs or the submitted Lightning Address values, so no account-to-submission correlation can be made offline.
- **Privileged upload event for user 77.** The supplied log says a merchant API key lacked file permission and the server key succeeded. Current route guards plus the new service-level owner/guest checks limit that path. The upload endpoint and parameters are fixed, and image type/size are bounded. This is a security-sensitive boundary and warrants deployment-version verification, but no evidence proves a guest or foreign merchant invoked it.
- **Webhook signature failures.** Incident notes describe missing/invalid signatures and missing secrets. The reviewed October 18 Laravel file did not contain matching signature-failure records; it did contain repeated callback-base-URL configuration errors. Code fails closed on missing secret/signature and invalid HMAC before write/job. Source alone cannot establish whether production requests were malicious, misconfigured, or delivered through a proxy with incorrect headers.
- **CashuMelt and guest registrations.** The HTTP 400 lifecycle issue is a code-level retry defect, but the supplied evidence does not connect it to new registrations.

### Infrastructure issues requiring live verification

- **Wallet configuration HTTP errors.** The supplied Laravel file has 15 `Wallet config verification failed` entries: five HTTP 530 around 02:20, five around 16:50, and five HTTP 502 around 21:10 UTC/local-log timestamps. This does not match the reported total of thirteen 502s; reconcile rotations, timezone, request window, and duplicate counting. For an existing connection with a baseline fingerprint, source returns on failed snapshot before changing fingerprint, verification timestamp, or drift fields; existing integrity tests cover preserving state on failure. The 502 source/availability and deployment behavior need live BTCPay/proxy/Docker evidence.
- **Webhook callback configuration.** The Laravel file contains 286 repeated `BTCPAY_WEBHOOK_BASE_URL must explicitly identify the reachable Satflux callback service` entries, approximately every five minutes through the day. This is a persistent callback configuration/health issue distinct from signature failure. The runbook asks for delivery and proxy aggregates.
- **Missing system alert destination.** The supplied file includes health transitions logged with `no SYSTEM_ALERT_EMAIL configured` (21 transitions observed). `SystemHealthAlerter` can send transition/recovery mail when configured; otherwise it records warnings. No alert configuration was changed.
- **BTCPay 302.** Older supplied BTCPay logs (October 5/13) show a 302 on the old web UI apps-list route; the October 18 log does not establish the same event. The actual `Location` is absent from the records. Current code avoids the route and will not forward credentials to a redirect destination.
- **Boltz gRPC failures and active swaps.** The source registries/repositories inspected contain no Boltz swap-management schema or Boltz-specific status endpoint; CashuMelt only classifies an external Lightning backend. No causal link to guest creation is evidenced. DNS/daemon health and active-swap exposure require the exact deployed plugin/daemon version and its documented read-only diagnostics.

### Normal application behavior

- A guest may exist without a real mailbox; this is intentional passwordless onboarding, with one store and one active Point of Sale app intended.
- A subscriber lookup returning 404 is the normal empty billing state for a user without a BTCPay subscription.
- A signed webhook for the configured subscription store may have no local `stores` row; the new identity exception preserves that architecture.
- A temporary wallet snapshot failure is not evidence that wallet configuration is invalid or changed.

## Security and reliability residual risks

- `TrustProxies` trusts `*`. If untrusted clients can reach the app directly or the edge proxy does not strip client-supplied forwarding headers, IP attribution and IP-keyed throttles can be spoofed. This does not bypass webhook HMAC. Confirm origin firewall and exact proxy header behavior; do not change trusted proxy ranges without the deployed topology.
- Guest rate limiting is IP-based and does not cap distinct fresh guest identities beyond request throttles. Do not add device fingerprinting or real-email requirements without a product/privacy decision.
- Guest creation locks only work across workers when the deployed cache backend provides shared atomic locks. Verify the deployed backend and the provisioning duration against the 30-minute lease.
- Webhooks without a `deliveryId` are accepted and can create duplicate event rows. Whether to require a delivery ID or add event-semantic deduplication needs BTCPay compatibility evidence.
- Boltz active-swap risk remains unknown until an operator supplies a supported aggregate diagnostic.
- No production configuration, account, wallet, payment, or plugin state was changed.
